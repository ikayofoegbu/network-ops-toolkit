# Three synthetic troubleshooting cases

These reproducible cases use simulated observations to exercise the toolkit's
report-generation and assessment paths. They cover DNS resolution failure,
TCP refusal and TLS certificate validation failure without network traffic.

From the repository root after installing the package:

```text
python examples/troubleshooting_cases.py all
python examples/troubleshooting_cases.py tls-failure --json
```

Each report includes `synthetic_demo: true`; text output prominently labels the
simulation. The renderer returns 0 when it successfully prints a case, including
an expected simulated failure. That is different from the live `netops probe`,
which returns 1 when requested connectivity or TLS validation fails.

## 1. Name resolution fails

[JSON report](../examples/cases/dns-failure.json)

Observation: `dns.status` is `failed`, `tcp.status` is `not_run`, and the
assessment is `dns_failed`. The report uses a fixed synthetic resolver code -2;
real resolver codes differ by operating system.

Known: this attempt did not obtain usable addresses. No TCP connection was tried.

Unknown: whether the hostname was mistyped, resolver configuration was wrong,
the answer was absent, a VPN changed the resolver, or a resolver/path was
unavailable. It does not establish that the application server is down.

Next useful check: confirm the intended hostname and the resolver actually used
on the affected device. If correct and authorized, inspect that resolver's
answer and compare the affected context with a known working context. Preserve
the original failure before changing DNS settings.

## 2. TCP connection is refused

[JSON report](../examples/cases/tcp-refused.json)

Observation: DNS returns documentation address 192.0.2.10, the port 443 attempt
records `refused`, and the assessment is `tcp_failed`.

Known: the simulated TCP connection attempt was refused. It did not time out or
establish a connection.

Unknown: which device rejected the connection, whether a service is listening,
or whether an endpoint/intermediary policy rejected it. Refusal alone does not
prove that the remote host generated the response.

Next useful check: confirm the intended endpoint and port. On a system you
administer, check the service's listening state; then inspect relevant endpoint
and intermediary policy evidence. Do not change firewall rules solely because
this report contains a refusal.

## 3. TCP works, but TLS validation fails

[JSON report](../examples/cases/tls-failure.json)

Observation: `tcp.status` is `connected`, `tls.status` is `failed`, and the
per-address TLS outcome is `certificate_invalid`. The simulated OpenSSL code 20
and message identify an issuer-chain verification failure. This is schema 2;
the first two cases use the unchanged TCP-only schema 1.

Known: the simulated TCP handshake succeeded and certificate validation did not.
The example deliberately preserves both facts.

Unknown: whether the service omitted an intermediate certificate, the selected
trust store lacks an expected issuer, an authorized inspection proxy presents a
different chain, or another condition applies. A certificate error does not by
itself establish an attack. Application health was not tested.

Next useful check: compare the presented chain and requested name with the
approved chain and the trust store used in that environment. Inspect chain and
validity evidence before changing configuration. Keep verification enabled;
disabling it changes the question instead of resolving the failure.

## Evidence boundaries

The stored JSON is generated by `examples/troubleshooting_cases.py`; automated
checks ensure it remains identical to current report generation and guard
against real DNS/socket use in the examples. Separate loopback integration tests
cover real TCP connections and TLS handshakes. Run the example renderer from the repository root after installation.
